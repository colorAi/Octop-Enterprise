# 企业版安全、管理性能与多进程更新计划

编写日期：2026-10-22。当前源码已包含访问边界、轻量查询、资源 manifest 与源发布、共享执行、分角色及多 worker 用户分片和空闲回收。各批次记录见第 11–15 节；实际部署、原生客户端及整机容量验收仍待执行，实施记录不等于全部阶段验收完成。

## 1. 本轮范围与约束

本计划统一安排三项更新：封堵员工读取管理员模型 API Key、消除用户管理与公司架构的阻塞、实现面向 4 核 4GB / 8 核 8GB / 8 核 16GB 的多进程运行。

按维护者要求保留当前密钥，不轮换、不重置、不修改密钥值。只修正访问与返回边界，保留管理员现有配置及员工通过服务端代理使用模型的能力。

保持现有产品版本，不提交或推送 Git。各阶段只运行修改模块及关联测试；容量测试使用独立数据和受控负载，不在日常服务上直接跑满负载。现有未提交工作全部保留，不按本次对话挑选源码丢弃其他修改。

本计划是实施和验收依据，不表示漏洞已经封堵或多进程已经上线。后续部署、客户端构建与实际测试结果分别记录。

## 2. 已确认的问题

| 问题 | 证据 | 更新目标 |
| --- | --- | --- |
| 普通员工可读取 API Key | 当前部署中，不具备 providers 管理权限的员工请求 `/api/providers` 得到 200；返回 Key 与服务器存储值一致。管理接口为 403、匿名接口为 401 | 后端阻止无管理权限员工读取凭据，保留现有 Key |
| 用户管理初次显示慢 | 7 个用户单独查询约 6ms；同时查询全部 13 个专家时，各轻量请求也等待约 1.1s | 用户列表先显示，专家状态读取不阻塞主事件循环 |
| 公司架构资源总览慢 | 专家/技能总览约 2.95s；存在资源扫描和逐员工部门核对 | 人员与资源目录分开，批量读取、按需加载 |
| 单进程状态无法直接复制 | 运行实例、会话锁、连接、取消、设备 Future 和调度状态在进程内 | 建立共享状态和唯一执行归属，再启用多进程 |
| 配置读取成本随资源增长 | 配置修订会读取定义与技能文件内容 | 保存时生成不可变资源快照，查询时比较版本，执行时核验新鲜授权 |

上述时间来自当前部署的定向诊断，不能用作 4GB 主机容量证明。多人部署的详细架构见 [多进程并发设计](multi-process-concurrency.md)。

## 4. 阶段一：封堵员工读取密钥

### 修改

- 对普通 `/api/providers` 列表补齐后端管理权限校验，与受控模型管理入口保持一致；没有模型管理权限的员工请求返回 403，不能仅隐藏页面菜单。
- 检查普通入口、管理入口及相关别名，避免存在另一条同样返回原始供应商记录的无权限路径。
- 审查补充：`/api/voice/providers` 同样返回凭据，必须与 `/api/admin/voice/providers` 一致要求 `voice` 权限；`providers` 权限不能替代 `voice` 权限。语音执行及活动提供商元数据入口保持现有访问能力。
- 员工选模型继续读取 `/api/providers/resolved` 等白名单元数据接口，不需要取得供应商 Key。
- 企业客户端继续使用模型代理，专家快照、配置更新响应和模型错误不包含真实 Key。
- 保留管理员及明确授权的模型管理账号现有管理能力，不扩展管理权限；不借本阶段改变数据库密钥存储、模型配置、启用状态或提供商地址。

当前漏洞影响的是普通已登录员工读取能力。封堵可以阻止今后的未授权读取，不能撤回此前已返回的内容；按维护者决定，本次不进行密钥轮换。

### 定向验证

1. 无任何管理权限的普通员工：`GET /api/providers` 和 `GET /api/admin/providers` 均为 403；未登录为 401。
2. 管理员仍能管理和测试已配置模型；员工模型元数据读取和既有代理调用继续有效。
3. 用非真实哨兵密钥验证员工响应不包含其值，覆盖正常响应、配置快照和相关错误；测试日志不能打印实际 Key。
4. 保存与本次无关的字段不清空 Key；修复前后在服务器内部比较密钥值，仅输出“未改变”的布尔结果。
5. 在当前部署用普通员工权限复核封堵结果，同时检查管理员管理流程。记录状态码和布尔结果，不保存真实响应体或密钥摘要。

相关测试优先放在 `tests/integration/test_providers_api.py`、`test_admin_providers.py` 及受影响的公司运行时用例，按修改范围选取。

### 完成条件

普通员工不能通过已检查入口取得完整 Key；管理员能力和员工正常模型调用保留；密钥值保持不变。不能以“前端看不到”替代直接 HTTP 验收。

## 5. 阶段二：消除管理页面阻塞与重复读取

### 2A：先解决用户列表

- 用户列表初次加载只取分页账号和必要的专家数量/归属摘要，不附带完整专家配置和容器探测。
- 全部专家列表移除同步逐实例初始化检查。展示使用明确的数据库/内存状态投影；需探测时通过有界后台 I/O 更新，详细状态按需获取。
- 不把可滞后的展示状态用于任务授权或认定某项任务已停止。
- 用户、角色、权限、专家明细分别加载，轻量人员列表不等待最慢的一组请求；保留已有内容完成局部刷新。
- 用户列表增加服务端分页与搜索，避免一次传回全部账号；管理员打开员工详情时再读取必要明细。
- 兼容约束：新增分页入口，不直接把旧 `/api/users` 的数组返回改为分页对象；员工专家明细按所有者过滤时仍须 `users` 权限。刷新保留已显示内容，翻页、搜索、切换账号/员工须取消或忽略过期响应。

### 2B：公司架构与配置查询

- 部门人员、资源目录、员工分配及运行状态分别查询；人员先显示。
- Go 增加受限的批量成员版本读取，消除总览中逐员工串行请求；批量数据只供管理展示，执行继续核对当前权威授权。
- 对工作区、Docker、同步数据库 I/O 统一做有界调度，避免同步操作占住接入事件循环，也避免无限线程排队。
- 配置内容改为保存时生成版本及不可变 manifest，读取只比较版本。同一源的技能清单和附件摘要不按每个员工反复扫描。
- 快照优化必须先覆盖全部写入入口并保护已发布目录；未迁移的旧源继续保留现有内容校验，不能仅增加 TTL 而放松源删除和撤权检测。
- 兜底轮询加抖动、合并重复请求；继续支持离线后重新进入时发现尚未应用的配置。

2A 可以先独立验收。2B 的快照写入边界完成后再启用快速路径；未通过前不得用缓存掩盖安全检查。

### 定向验证与目标

- 用慢 Docker/工作区返回模拟阻塞，确认用户、权限、取消等轻量请求仍可并发返回。
- 覆盖分页、搜索、空结果、禁用账号、详情加载、部分请求失败及用户切换。
- 验证快照的专家字段、提示词、定义、技能脚本与附件一致性；删除、撤权、调岗仍在下一次受控调用生效。
- 重新测量真实 HTTP 的单独与并行请求，记录前后 p50/p95/p99；测试规模和硬件条件同时记录。
- 候选目标：分页列表 p95 ≤ 500ms，配置版本读取 p95 ≤ 200ms；不能只凭一次请求截图宣布达标。
- 实际页面检查：用户先显示、刷新不整页清空、明细失败有明确反馈；服务端读取不再随用户逐个访问所有容器。

优先验证 `UsersListPanel`、`CompanyStructure`、专家/用户 API、资源修订、通信批量查询，以及它们现有的前后端关联测试。

## 6. 阶段三：建立多进程共享状态

本阶段先建立正确性，不能直接复制多个完整 `OctopServer`。

- PostgreSQL 保存任务、幂等键、会话执行占用、运行时归属、取消/审批命令、事件与 outbox。
- 网页、员工桌面、定时任务、人工审批恢复共用会话执行规则，防止多入口同时写同一会话。
- 运行时按用户归属，专家按需加载。租约、启动代次和递增 token 防止旧进程写回；确认旧执行者停止后才移交可写工作区。
- 在开始阶段三的迁移和领取实现前，落定任务/命令状态转换、幂等键作用域、事件游标，以及旧执行者/子进程停止确认的具体接口与证据；租约超时本身不能作为停止证明。
- 使用短事务和队列领取；模型请求、工具和客户端等待期间不持有长数据库事务。
- 设备连接记录代次，工具操作有独立编号和回执；socket/Future 丢失后能核对，结果未知不自动重放。
- 配置、账号和授权变更跨进程可见，关键鉴权不依赖另一个进程尚未失效的缓存。
- 设置全局模型并发、用户公平调度、额度预留、队列与内存上限，避免进程数增加后各自放大额度。
- 通知使用 PostgreSQL `LISTEN/NOTIFY` 唤醒，持久事件用于补读；Redis 暂不作为必装组件。
- 定时任务、渠道订阅、身份投递、备份与维护明确归属；同一计划时间只能生成一次任务。

### 完成条件

至少两个独立进程竞争同一会话、重复提交、取消、审批恢复和事件投递时，数据库状态正确。旧 token 写回被拒绝、已完成工具不重复执行、通知断开可补读、员工数据不串号。通过真实 Go/PostgreSQL 关联联调后进入阶段四。

## 7. 阶段四：形成最小多进程部署

新增按角色启动的应用入口，沿用同一镜像与 Compose。

| 角色 | 职责 | 不重复启动的内容 |
| --- | --- | --- |
| 接入 `web` | HTTP、登录、管理读取、WebSocket、设备连接、任务提交和事件投递 | 全量专家、任务执行、全局定时调度 |
| 任务 `worker` | 所属用户运行时、模型代理、工具和后台任务；其中一个持有调度领导权 | 其他进程已持有的运行时、连接与定时项 |
| 既有 Go 通信 | 企业通信与部门权威数据 | 本阶段不直接复制进程内实时 hub |
| 一次性初始化 | 迁移、密钥读取/必要的首次初始化、目录准备 | 不在每个副本重复执行迁移和安装依赖 |

先启用 **2 个 web + 1 个 worker**。每个容器一个 Python 进程；多个用户共享进程，每人独立 Agent 的数据和执行身份保留，空闲 Agent 不要求独占常驻进程。

按角色限制数据库池、线程池、上传及事件缓冲。连接池上限按应用库和通信库合计计算；日志不多进程抢写同一个轮转文件，维护 CLI 按归属路由。

跨进程连接、取消和任务路由不能依赖 HTTP 粘性会话。先在保留现有公开路由和事件兼容性的条件下接入；新增排队/补读能力采用能力协商，明确旧客户端行为和需要重建的资源。

### 完成条件

两个接入进程分担请求时，任意请求都能找到正确任务和设备。终止一个接入进程后可重连补事件；终止任务进程不会重复副作用。调度不重复，管理员撤权即时生效，登录、消息、桌面任务和管理员操作通过真实联调。

## 8. 阶段五：资源档位和人数验收

| 资源档位 | 接入/任务进程起步配置 | 在线人数首轮验收目标 | 服务器任务并发保护初值 |
| --- | --- | --- | --- |
| 4 核 4GB | 2 / 1 | 50 人 | 全局 2 |
| 8 核 8GB | 2 / 2 | 100 人 | 全局 4 |
| 8 核 16GB | 3 / 3 | 200 人 | 全局 8 |

在线人数是待测目标，不是已验证能力；包含持续连接和正常交互，不能只开空 WebSocket。它与所有人同时执行模型任务的数量不同。模型提供商容量、员工本地执行、服务器重任务分别计量，队列等待和拒绝率必须报告。

- 在独立同规格主机/虚拟机上测试整个栈，包括操作系统、容器引擎、代理、Python、Go 和 PostgreSQL；不能只限制 Python 容器内存。
- 先用可控模型流测试平台，再做受控数量的真实模型请求和真实员工客户端链路，不把模型供应商瓶颈混成平台响应延迟。
- 覆盖读列表、配置轮询、聊天/设备连接、任务提交与取消、技能更新、调岗撤权、长流、大请求和慢工具。
- 在线数与任务到达率分别阶梯递增；同时做固定到达率测试，避免系统变慢时压测器自动少发请求。
- 每个候选档先稳定运行至少 20 分钟；容量点增加 2 小时稳定性测试，最终配置做 24 小时观察。
- 注入进程退出、数据库暂不可写、通知断开、设备重连、重复请求和迟到回执，验证恢复及正确性。
- 内存预算参考架构文档：约 3.4 / 6.8 / 13.6 GiB，均为待验证预算；大模型推理等额外服务另计。

候选 SLO：列表 p95 ≤ 500ms，提交/取消确认 p95 ≤ 300ms，接入事件循环 p99 ≤ 50ms；正常负载意外 HTTP 5xx < 0.1%，无 OOM、持续内存增长、越权和重复执行。不得通过大量拒绝任务来宣称人数达标，任务接受率、等待时间和完成率也必须满足确定的验收预算。

每个规格最终记录：建议在线人数、可持续请求率、可并行任务/模型数、排队等待、最大内存、故障恢复结果和不适合的任务类型。通过多少写多少，不预先承诺上表目标必然达到。

## 9. 部署与回退安排

1. 每阶段保存代码/构建标识、测试结果和数据兼容范围。候选源码使用既定导出工具包含完整工作区及新增测试，继续维护唯一待发布入口。
2. 阶段一优先安排独立切换，不等待架构改造。切换前检查活动任务，保留原镜像和配置；不修改供应商 Key。
3. 存在数据库/任务格式变更的阶段，先在临时 PostgreSQL 库验证迁移和恢复，再取得可恢复备份。迁移只执行一次。
4. 多进程发布先停止新领取、排空和核对活动任务，再切换归属；旧单体与新 worker 不得同时消费同一执行域。
5. 回退前确认旧代码支持当前 schema；不支持时按匹配快照恢复并保留新增结果。不能仅把新实例缩为一个副本就认定已经回到旧架构。
6. 服务端、网页资源、员工客户端、工具运行时分别记录是否更新；需要新客户端能力时同步交付，不把服务端通过等同于原生客户端通过。

不因编写或实施本计划自动升级版本、提交 Git、推送或对外发布。实际构建、切换及检查结果追加到对应阶段的验收记录中。

## 11. 2026-10-22 审查与首批实施记录

### 审查结论

阶段顺序、先共享状态再多进程、保留授权实时核验的方向可行。发现并补入语音供应商凭据入口遗漏；补充分页兼容边界和阶段三的执行者停止证明要求。后续容量验收仍须先固定任务组合、到达率、接受率及排队预算；当前在线人数仅作为待测目标。

### 本地源码实现

- 两个普通凭据列表入口分别要求 `providers` / `voice` 权限，与各自管理入口一致；保留无管理权限员工的模型选择、语音活动元数据及企业模型代理。

- 默认空闲 300 秒后卸载 Harness、关闭记忆运行时并停止沙箱，保留启用状态、文件和历史。HTTP 流/后台写入、终端、发布、IM 附件与主动关怀持有活动引用；排队、运行、审批、取消中、unknown、历史维护及本地活动调用均阻止回收。下次访问重新加载同一工作区；停止失败不丢弃句柄。
- 修复真实并发首轮对话暴露的检查点建表冲突：init 先迁移共享检查点，迁移锁使用短查询尝试取得锁，避免等待锁的快照阻塞并发建索引。补齐 IM 媒体入口按次获取工作区，避免回收后复用关闭的句柄。

## 16. 2026-10-23 沙箱总内存准入

- 同一执行域的全部 worker 共用数据库预算，按沙箱完整 cgroup 内存上限在创建/恢复前原子预留。三档单沙箱/总预算分别为 256/512 MiB、384/1536 MiB、512/4096 MiB，增加进程不会放大预算。init 保存配置，新 web/worker 校验初始化标记；旧 schema 29 的幂等补表与停止核验兼容，版本仍为 `1.0.1b2`，schema 仍为 29。
- 卷初始化容器与主容器串行执行，共用一个预留，初始化最多 128 MiB，两者均限制内存和 swap。重复获取同一容器不会重复计费，重新预留生成新 token；旧句柄不能释放新一轮额度。Docker 响应不确定、进程失联或租约过期保留占用；仅确认停止后释放。
- 不足时返回可重试的 `SANDBOX_MEMORY_EXHAUSTED`，提交共享回收信号，各 worker 可提前回收空闲实例。持久任务、审批、未知结果、HTTP/后台写入和本地活动保护继续生效。启动前拒绝保存明确失败回执并释放会话，不把已启用 Agent 标记为损坏；配置重载不足保留待更新状态。
- 183 项关联回归通过，随后 76 项执行/预算/回收补验通过，两组存在重叠；独立 PostgreSQL 17.11 的 10 项通过，包括 4 个进程同时发起 16 次预留仅准入 2 次，以及旧 schema 29 的停止证明和幂等补表。15 个 Python 文件通过 Ruff/格式检查，11 个源文件通过 mypy；中英文错误码一致性、网页构建及三档 Compose 配置通过。仅运行受影响模块及关联验证。
- 两个独立当前源码进程连接同一个临时 PostgreSQL 并实际启动 Docker 沙箱，280 次采样中的运行容器 cgroup 上限总和与预留峰值均为 512 MiB，没有超出配置预算。验证第三个沙箱被拒绝、确认回收后另一个进程使用释放额度、休眠恢复保留文件、意外停止后恢复不重复计费、租约过期不释放及旧 worker 拒绝新启动。临时容器、卷和数据库已清理，现有部署未修改。

## 17. 2026-10-23 按需专家与同事通信隔离补验
